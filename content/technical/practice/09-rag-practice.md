上半场：按第 08 节作业，把杭州导游知识库从 0 到手把手走一遍。下半场：十三老师加餐讲 RAG（字节跳动、杰越星辰做过一年 AI 产品经理，最早在火山引擎做 RAG）。群里有 IT / AI 工程师背景的同学想听更深，所以加了这一段。

> 知识库它只是一个工具，工具它是为了解决问题而存在的。

## 一、知识库是工具，不是目的

搭库之前先问：客户为什么需要它？要覆盖哪些问题？作业要求做出**最小可用**的杭州导游 AI 知识库：能按时间、预算、兴趣推荐景点，能说清位置和场景，能给出火车站 / 机场 / 地铁到主要景点的基础公共交通方案，还要有小红书真实种草。

假设对面是一家杭州景点相关公司，至少五类需求（后两类常被漏）：

| 需求 | 库里要装什么 |
| --- | --- |
| 景点推荐 | 知名景点盘点、特色、适合场景、内部政策、价格 |
| 路线规划 | 距火车站 / 机场 / 地铁方便的点；一日游 / 两日游常规路线 |
| 预算盘点 | 主流甚至小众景点价格、每个价格对应哪些项目、服务内容、时间周期 |
| 适用场景 | 约会（两人、偏安静或偏刺激）、公司团建、出片机位和拍摄要点 |
| 真实种草 | 小红书笔记 + 评论区对比，先判断是不是商单；每个景点大约 3～5 篇 |

把这些写成提示词，再发给 WorkBuddy，比「把一堆资料丢进去」重要。中间的拆解过程，才是 FDE 要练的能力。

> 你直接丢给他的话，你中间的思考过程可能就没有了。因为我们如果后面要去做企业服务……你怎么样去拆解这些问题？这个是我们需要锻炼的能力。

原版作业写得很细，例如杭州景点库不少于 12 个点，每个点写清名称、类型、推荐季节等。老师后来删模糊了，是怕大家把说明书整份丢给模型、丢掉「自己拆问题」的训练。FDE 卖的是拆解，不是提示词粘贴。

## 二、和 Agent 协作的节奏

### 1. 先把上下文说全，再开计划模式

老师习惯语音输入：手打一分钟大约 100 字，嘴说可以 300 字。豆包输入法偏流式、少丢细节；微信输入法会分点整理，但容易丢上下文。远程电脑（ToDesk）可剪切板互通；UU 远程免费但不互通剪切板，土办法是语音转文字发到自己飞书再粘贴。千问输入法会自动进剪切板，配合 ToDesk 更顺。

提示词里除了五类需求，还要补两句标准：

- 搭完之后，朋友来杭州，能快速推荐合适、舒服、有真实评价的景点和路线，方便带人接客
- 让它调研资料从哪收；小红书有反爬和封号风险，要它推荐相对安全稳定的接口方案（API / MCP），不要自己瞎爬

WorkBuddy 里先开**计划模式**，模型课上用的是当时最聪明的 **K3**。它会回选项，课上的选择是：

| 决策点 | 课上选法 |
| --- | --- |
| 载体 | 飞书多维表格（也可 Obsidian / 本地 Markdown） |
| 范围 | 杭州市区 |
| 种草采集 | MCP 半自动（登录后以你的小红书身份抓；注意控频率，机械高速采集容易封号） |
| 交付 | 先做最小可用样板，再扩 |

老师会把自己 Obsidian 里的工具清单也丢给它，让它在本地合集里找小红书 MCP，而不是两眼一抹黑上网搜。执行中要盯着：登录失败、Computer Use 窗口不对，就纠正方向。Codex 可以中途按 Enter 改方向；WorkBuddy / Claude Code 当时还不行，只能先停再发。

复杂任务要开多个窗口并行——老师说自己可能开 10 个。人的工作变成：指导、审查、看有没有干偏。

### 2. 目录按需求切，接口让它自己接

一个需求一个目录，这是最高频、最普适的分类：

- 景点推荐 → 按景点
- 路线规划 → 按交通
- 预算 → 景点项目价格
- 适用场景 → 场景方案
- 种草 → 种草帖子
- 另加：来源标注、**检索测试题**单独文件夹
- 再加：README（说明书，知识库解决什么问题）+ MOC

接口两块，能少手搓就少手搓：

1. **IM 连接器**：WorkBuddy 对飞书、钉钉、企微有连接器。不行就自然语言：「帮我下载安装飞书 CLI，发起授权」。课上建议**一次性全量授权**，否则每个新任务都喊没权限。授权后把飞书妙记链接丢给它，就能读逐字稿、当课程助教，不必点进妙记 → 导出文字 → 再上传
2. **浏览器**：装 CDP / 浏览器自动化 Skill，让它控 Chrome。装好后不必再靠一堆浏览器插件。规则可以写成：不要新开窗口，直接操控已登录的旧浏览器，避免反复扫码

去重冲突的默认标准：**以最新为准**（去年票价和今年票价，用今年的）。官网文旅信息、景区公告、公开的地铁公交高铁机场、小红书帖子，收完统一成 Markdown，再按景点拆目录。README、MOC、子目录都可以让 WorkBuddy 写，人把要求说清即可。飞书云文档本质是文本，可下载为 Markdown。

进阶才是包 Skill、做成网页应用（群里已有同学做）。主路径仍是：问题清单 → 采集清洗 → MD → 目录 / 链接 → 10 道检索题。

### 3. 降维提示词

名词听不懂时，课上最常用的一句：

> 用村口 60 岁大爷也能听懂的话解释。

把第八节妙记丢给接了飞书 CLI 的模型，再加这句，它就会把 Markdown、切片、向量化、RAG 讲成人话。本来计划做小程序课程助手，ICP 备案太久还没上，先用这一招当助教。

## 三、RAG 的大白话（上半场 + 十三老师）

先把两套比喻叠在一张表里。曲老师用「村委会账本 / 撕纸条 / 指纹」；十三老师用「热水器说明书 / 小抄 / 开卷考试」。

| 术语 | 人话 |
| --- | --- |
| Markdown | AI 最顺眼的统一草稿纸。村委会收来的账本有的写在烟纸盒、有的是 Excel、有的是微信记录；PPT / PDF / 录音都先抄成它 |
| 切片 | 公司台账太厚，撕成一张张小纸片；说明书真正管用的往往只有那半页 |
| 向量化 | 每张纸片按一个「指纹」——电脑不懂意思，但懂数字，把「今天天气真好」编成一串号码 |
| 检索 | 按指纹找最像的几张（号码挨得近 = 意思近）。「老王爱吃什么」对不上关键词「偏爱甜瓜」，关键词检索会漏，意思检索能中 |
| RAG | 开卷考试：先找到纸条，再对着纸条回答。三个字母 = 检索、增强、生成，人话是**查、加、答** |
| 向量数据库 | 放纸条的柜子 |

没有检索的对话是闭卷，模型只能靠训练记忆猜。朋友学问再大，没见过你家热水器，修起来头头是道也对不上。把说明书整本塞给他，书越长越难翻到那半页。RAG 就是只递正确的那半页——**小抄**。

> RAG 它并不是让 AI 变聪明，而是我们要去给它递一张小抄。

为什么本地 Obsidian 有时不够：模型能装的上下文有限，像人很难立刻想起十年前的细节。笑傲江湖全书演示里大约两兆，企业库可能到数 TB。早期模型只有 64K、128K 窗口，只能切开再找。库很小（例如 10 篇、十万级上下文）时，全文丢进百万窗口的模型和 RAG 差别不大；库一大，才必须上向量检索。

Obsidian 更像把原始资料直接跳到「交给 AI」；完整 RAG 中间还有拆纸、编号、进柜、问题编号、找近邻。课上说：可以把它理解成「简化版 RAG」，但逻辑不一样。

## 四、十三老师的八步 + 三个会出错的地方

构建柜子（前四步）+ 回答问题（后四步）：

1. 有一份原始资料
2. 拆成一张张小纸片（每张带着原文、号码、来源，才能回原文核对）
3. 给每张纸编号（向量化）
4. 收进柜子（向量数据库）
5. 用户的问题同样编号
6. 找出意思最近的几张小抄
7. 问题和纸片一起交给 AI
8. AI 按资料组织回答

现场 demo 用《笑傲江湖》做成 3D 点云：每个小球是一张小抄。问「令狐冲的独孤九剑是跟谁学的」，会亮出若干最相关片段，再和问题一起发给 DeepSeek，答案会写「根据资料……」。小抄数量可调：少到 1～3 张，或多到 10～20 张。多给几张，通常更稳。

平台实操走的是 **FastGPT**（开源知识库产品，群里发了链接）：

1. 登录 → 知识库 Tab → 新建通用知识库
2. 上传资料，设切片规则（按 100 字 / 1000 字 / 1 万字等）
3. 预览分块（课上一个精简文档自动切成 72 个小抄；更长的测试切过 926 段）
4. 索引向量化 = 编号 + 收进柜子
5. 用「搜索测试」看问题命中了哪些片段

FastGPT 这套界面主要做完前四步（把柜子建好）；把切片再发给大模型，很多产品要外接模型 API。群里另有一份最小 Python 实现，对应这八步，不懂代码可以整份丢给 AI，按步骤追问。索引（embedding）模型：最早是 OpenAI，国内火山方舟 / 豆包、阿里也有课上点名的选项。

三个容易错的环节：

| 环节 | 会怎样 |
| --- | --- |
| 分块 | 切太长或太短，找不到正确那半页；切片还可能**丢信息** |
| 编码 | 号码编不准，找到错误纸条 |
| 生成 | 小说都递到面前了，模型仍不按资料答 |

让它找得更准，课上给的办法：多给背景（保留上下文）、多找几张小抄、回答时标出资料来源。进阶技巧只要求知道名字，不要求当场会调：按标题建索引、相邻切片适度重叠（overlap）、多路召回和重排、编号还原回原文。

记住三句就够：

1. RAG = 先查再答，先拿小抄再让 AI 答
2. 号码挨得近，意思就近
3. 找出来的小纸片准不准，决定最后答得准不准

### GraphRAG 和本体论（加餐口径）

普通 RAG 把小抄按编号放进柜子，不太描写纸条之间的关系。GraphRAG / 知识图谱会量化关系：例如「我是老王」和「老王喜欢喝咖啡」是关联的。本体论再往上：多张小抄可归成一类（「老王爱吃什么」vs「老王喜欢做什么」），还可能叠数据库等理论。效果更好，但成本、存储、复杂度都高。这是第 08 节说「图谱太重」的同一条线。KAG 等变体课上只点名，不展开。

## 五、上半场收尾时导游库长什么样

等采集跑完，飞书里可以出现景点总表、预算速查表、场景匹配等**多维表格**——这也是一种搭库方式，不一定全是长文。根目录下有文档 + MOC（哪些文档在哪个位置）。Browser Skill 用来自动操控飞书和浏览器。

加餐作业：按群里步骤体验一遍 FastGPT，把中间过程录屏提交。向量库往往是本地部署、或库已经庞大时再上；知道流程、能给客户讲清楚即可。

## 六、作业标准：即使原版被删过，自己仍该拆到这一层

老师说原版 README 连标准都写好了，后来删模糊，是怕大家失去拆解训练。你自己练习时，仍建议把最小可用拆到可验收：

- 景点库：不少于 12 个点（原版数量）；每个点至少有名称、类型、推荐季节、政策、价格、适合场景
- 交通：火车站、机场、地铁到主要景点的公共交通，以及一日游 / 两日游各一条常规线
- 预算：价格对应到项目和服务内容，不要只有一个「门票 XX 元」
- 种草：每点 3～5 篇，附评论对比和「是否商单」判断
- 来源：官网 / 文旅 / 小红书链接单独可追溯（接第 03 节「可追溯」）
- 测试：10 道题覆盖推荐、交通、预算、场景、种草；答不出就回去补，不要先包装网页

群里有人做成网页应用是加分项。主路径走完再包 Skill。采集阶段的冲突（去年票价 vs 今年票价）写死「以最新为准」，并在 MOC 或 README 里声明。

## 七、把「小抄」讲给客户的完整例子

给客户解释时，可以按十三老师的热水器故事一口气讲完，不要先丢 FastGPT 截图：

1. 你有个特别有学问的朋友（大模型），问什么都张口就来
2. 问「我家热水器怎么修」，他讲得头头是道，你照着做全错——他没见过你家那一台
3. 你把说明书递给他，他必须整本翻到「故障处理」那一章，再按书回答
4. 说明书越厚，真正管用的往往只有半页，找半页的时间比修还长
5. RAG = 不要整本书，只把正确的那半页撕下来递过去
6. 半页怎么找？不能只靠字面「爱吃」去对「偏爱甜瓜」，要把每段话编成号码，按意思的距离找
7. 找到的半页（小抄）和你的问题一起交给模型，这才叫开卷

曲老师上半场的「村委会账本」可以接在第 3 步前面：账本格式不一，先统一抄成 Markdown，再谈撕纸。两套比喻不要混用角色，但可以叠：先统一草稿纸，再撕纸、按指纹、开卷。

现场若被问「那我 Obsidian 不就行了」，用课上口径答：文档少、总字数远小于窗口时，全文丢进去和 RAG 差不多；企业到 TB 级、或模型窗口只有 64K / 128K 时，中间六步（切片、编号、进柜、问题编号、近邻、拼小抄）才是快速检索。知识图谱能描述纸条和纸条的关系，效果更好，但字节 2024 年知道、至今没做，因为太重——FDE 默认先 RAG，不先卖图谱。

FastGPT 群里的操作文件和《笑傲江湖》语料，用来感受「72 个小抄 / 926 个分段」和搜索测试，不要求这节就给客户上线一套自研 RAG。代码层那八步，看不懂就把最小实现丢给 AI，按「这一段对应第几步」追问。加餐的定位是：知道有这个技术、知道柜子怎么建、知道切完之后还要把纸片发给模型。

## 常见坑

- 作业说明书整份丢给模型，自己不拆需求
- 目录按「我以为的旅游分类」切，不按客户问题切
- 小红书机械高速采集，不控频率
- 飞书权限舍不得一次授满，后面每个任务卡授权
- 冲突内容不写「以最新为准」
- 库只有 10 篇就上企业级 RAG，浪费复杂度
- 只建 FastGPT 知识库，以为八步都做完了（可能只做了前四步）
- 切片过碎导致信息丢失，却不回头调分块和重叠
